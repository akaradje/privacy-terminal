The pre-registered falsifiable expectation fired: *"if NYM > 55 then the coverage genes are not

discriminating metadata-only privacy"*. NYM scored 64, second overall, ahead of ZEC.

Why NYM ranked second (evidence, not opinion)

The fill gave NYM hs=1, hr=1 on the grounds that a mixnet hides the sender/receiver of

communication. But hs/hr/ha are defined in rubric.json as hiding the sender, receiver and

amount of an on-chain transfer — NYM does not do that at all. Its ha=0 was the only penalty,

and ha is one of four equally weighted genes inside the 30-point coverage component, so it lost

only ~7.5 points while collecting full marks on hmeta (10), hnet (8), man (12) and mat (8).

This is a rubric defect, not an engine defect: the rubric has no rule for systems with no

on-chain value transfer.

Conclusion: the pilot round does not pass. The engine and schema work; the rubric and the

evidence procedure do not yet support a defensible fill.

5. What must change before filling all 51

  1. Rubric: add a rule for systems with no on-chain value transfer. hs/hr/ha must score 0 for

them and be excluded from the coverage denominator (the same way nst excludes hst), so a

mixnet is judged on hmeta/hnet instead of being credited for hiding transfers it does not hide.

  1. aset needs an evidence procedure, not a hope. Either (a) define a repeatable measurement

(explorer query + date, recorded as src), or (b) accept aset as a "measured" field that is

allowed to be null in the first pass, with the bits weight redistributed instead of silently

widening the band.

  1. The band gate needs restating. With several low-confidence genes, a global band ≤ ±10 is not

reachable without either better evidence or a per-component confidence rule (e.g. require

conf ≥ med on the three heaviest available components).

  1. Three of my own calls need a second opinion before they harden into data:

ZEC hs/hr/ha = 1 (opt-in) rather than 2 · AZTEC man = 0 because public functions exist ·

NYM man = 1 and hs/hr = 1 (the modelling question in item 1).

  1. Retraction: my earlier statement "ZEC 62 vs XMR 79 ยังออกมาถูกทาง" is withdrawn. This

pre-registered run shows the opposite for NYM, and that is the more useful result.

6. Where the evidence came from

Every non-null value carries src + asof (2026-10-16) in data/dna3.json, pointing at the

project's own specification or documentation: Zero-to-Monero, the Zcash protocol spec (ZIP-224 /

Halo 2), Aztec docs, Secret Network docs, Partisia docs, Nym docs, and the Monero research-lab repo

for the anonymity-set literature. Confidence is marked honestly: high where the source states the

claim, med where it is derived, low where it is an inference — the low-confidence values are

listed above and are the reason MPC's band reaches ±14.

Pilot round 2 — after rubric 2.1 (arch roles + aset precedence)

Run: 2026-10-16 · rubric 2.1.0-preview · supersedes §1–§4 of pilot/result.md

What changed in rubric 2.1

  1. Non-value-transfer rule. Every asset carries arch = value-transfer | transport | compute.

A token that lives on a transparent host chain scores hs/hr/ha = 0 — the secrecy of its data

packets is not the secrecy of its transfers, and is captured by hmeta/hnet instead.

  1. aset precedence, in fixed order. (1) protocol-enforced per-tx set (e.g. Monero ring size = 16

at consensus level) → (2) live pool depth at asof (note/UTXO count or % of supply) → (3) fallback to

the lowest band when the claim is unverifiable.

  1. Unverifiable cap, enforced in the engine. An aset with no src or conf = low has its bits

contribution capped at the < 1,000 band, so an unbacked claim cannot buy credit.

  1. Separate leaderboards by arch (the reviewer's Option B) — value-transfer assets are not ranked

against infrastructure assets, because their gene sets mean different things.

Review of the proposed v4 upgrade plan

Reviewed: 2026-10-16 · context: the pilot round just failed its gates (pilot/result.md)

Verdict in one line

The plan is directionally right but mis-ordered: it proposes four new capability layers on top of a

scoring core that has not yet passed a single validation gate. Two of its technical items are also

wrong for this codebase. Build the foundation first; the plan's §2–§4 become meaningful afterwards.

Blocking dependency (what the plan does not account for)

GateStateConsequence for the plan
Rubric has no rule for systems without on-chain value transferopen defectany new pillar inherits the same class of modelling hole (NYM ranked 2nd because of it)
aset has no repeatable measurement procedureopen§2 "Anonymity set size" cannot be filled without inventing numbers
Evidence coverage72 / 364 values (20%)§2's new metrics would be added as unsourced numbers, which the data contract forbids
Pilot gates (coverage 100%, band ≤ ±10, order, stability)failed§3 alpha features consume scores that are not yet trustworthy
history/ depth1 day§3.1 (30–90 day divergence) and §3.2 (rotation) are arithmetically impossible today

Triage

Do first (unblocks everything else)

  1. Fix the rubric defect — add a "no value transfer" rule so hs/hr/ha score 0 and are excluded from

the coverage denominator for mixnet/dVPN/messenger assets. (data/schema/rubric.json)

  1. Define the aset evidence procedure — one measurement recipe per mechanism family (explorer query +

date recorded as src), or explicitly accept aset as null in pass 1 and redistribute the bits weight

instead of silently widening the band. (data/schema/rubric.json + engine/score.js)

  1. Re-run the 6-coin pilot against the gates — including the blind second pass that has not been done.
  2. Then fill the remaining 45 coins with src + asof.

Do next (the plan's §2, in blueprint order)

  1. Pillars D (development vitality) and L (liquidity) — both are API-derivable, low ambiguity.
  2. Pillars T (tokenomics) and S (security/decentralisation) — partly curated, partly API.
  3. Pillar R (regulatory) — fully curated, and the most judgement-heavy; do it last of the six.
  4. Anomaly detection in validate.py — the plan's §4.4 is a genuinely good idea and cheap: reject

mcap == 0, volume == 0, or a >90% day-over-day jump against history/, and flag instead of ingest.

Do later (blocked by data depth, not by code)

  1. §3.1 dev-vs-mcap divergence — needs ≥30 days of history/ with pillar scores in it. The history

snapshot already stores genes/flags/pillars, so the data will be there; the code would be premature today.

  1. §3.2 sector rotation — same dependency; the category snapshots exist but a single day cannot show flow.
  2. §3.3 time-series compaction — worth doing once history/ has ~14+ files, not before.
  3. §4.3 head-to-head radar — the radar needs the seven pillar scores; today only P exists, so a radar

would render one axis. Build after items 5–7.

Won't do as proposed (with reasons)

  1. "Rewrite the fetchers as async and CI drops to seconds." False for this project. The fetcher is not

CPU- or latency-bound; it is rate-limit-bound. Measured on 2026-10-15: 51 dossiers took ~35–40 minutes

with an 8 s sleep and 75 s backoff on HTTP 429. Concurrency does not raise a rate limit — it triggers

more 429s and can get the IP throttled harder. The correct fixes, in order: (a) a CoinGecko Pro key

(the plan omits this, and it is the only change that actually solves it), (b) fewer endpoints,

(c) ETag / If-Modified-Since to skip unchanged payloads, (d) jittered backoff. Async is a fine

implementation detail after those; it is not the bottleneck.

  1. GitHub GraphQL — reasonable but low-yield here: gh CLI calls are authenticated at 5,000 req/h and the

enrichment is ~50 calls. Worth doing when the pillar-D metrics need per-repo commit/contributor history,

which REST makes awkward. Not a priority on its own.

  1. Web Workers for custom rubric weighting — solves a non-problem. Scoring 51 assets × 12 genes is

microseconds; there is no jank to remove. Moving engine/score.js into a worker adds a message-passing

boundary and a second code path for zero measured benefit.

  1. Lazy-loading the detail JSONs — genuinely improves first paint (the bundle is now 241 KB because every

dossier is embedded), but it breaks two stated design goals: single-file distribution and offline use.

Treat it as a deliberate trade-off, not a pure win: either accept the bundle size, or ship a second

"online" build variant. Do not silently drop the offline property.

Answer to "which file should we start with?"

Not a file — data/schema/rubric.json. Every other item in the plan depends on the rubric producing

values that two independent researchers would agree on. Adding pillars, alpha features or a faster pipeline

before that simply multiplies the number of unsourced numbers in the system.

CHANGELOG.md · raw

Changelog

All notable changes to the scoring engine and data contract.

scoring_version is written into every build (STATS.scoring_version) — the formula lives only in engine/score.js.

2.0.0-preview — 2026-10-15

DNA v2 engine + red-flag engine, added on top of the published v1 scoring.

Added

  • engine/score.js: 12-gene DNA v2 (adds hmeta, hnet, mat, pq, aset; man accepts 0.5 = default-on; tl is 0–2), anonymity set measured in bits (log₂(aset) / 20), evidence confidence band, four weighting presets, rankStability().
  • engine/flags.js: 14 red-flag rules (CRITICAL/HIGH/MED/LOW) + metricsFor().
  • data/schema/curated.schema.json: gene values may be bare numbers (legacy) or {v, conf, src, asof, note}.
  • scripts/snapshot_history.py: daily history/YYYY-MM-DD.json.gz snapshot (scores + prices) so rankings can be compared over time.
  • CHANGELOG.md (this file).

Fixed (review of the first v2 draft)

  • Missing data is no longer zero. A gene with no value is null; the score is computed over the available weight and rescaled to 100. coverage and insufficient are reported, and v2 is labelled PREVIEW in the UI until coverage passes 80%. v1 remains the score the UI ranks on.
  • aset now has one definition for every mechanism family (effective per-transaction anonymity set), documented in engine/score.js and the schema. Ring-based coins legitimately score low on this one component and recover the difference through man.
  • Band capped at ±25 and scaled by evidence quality plus missing weight (it used to reach 48, which made it useless for decisions).
  • brk verified as a −15 penalty, not a reset: XMR-like 79 → 64.
  • DERO repo false positive: CoinGecko pointed at deroproject/derosuite (archived 2022), which triggered CRITICAL dead_repo. REPO_OVERRIDE in data/enrich_gh.py now pins the maintained repo deroproject/derohe (last push 2026-08-21).

Changed

  • validate.py no longer errors on a missing src (it warns and treats the value as conf = low, per the blueprint) and now also counts bare-number genes, reporting evidence coverage as a percentage.
  • validate.py never re-implements the formula: it shells out to node engine/score.js.

Known gaps

  • Evidence coverage is 0%: all 330 gene values are still bare numbers. Phase 2 fills them with src + asof.
  • Pillars S/D/T/L/R/U are not implemented yet (only P).
  • history/ starts empty — the first snapshot lands with the next scheduled refresh.

4. DNA framework (หัวใจของโปรเจกต์)

4.1 เกณฑ์อยู่ใน pure list (data/tiers.json)

privacy เป็นแกนหลักของโปรโตคอล และ มีเอกสารเทคนิคยืนยันกลไกได้ — ไม่มี "หวังว่าใกล้มา" เช่น xVG (IP-level) ก็ยังอยู่เพราะมีเอกสารชัดเจน แต่ถูก gene flags บอกให้เห็นว่า ha/hr/hs=0

4.2 สูตรคะแนน (คำนวณสดฝั่ง client, โปร่งใส)

denom = 8 - (nst ? 2 : 0);                       // สกุลเงินล่วงไม่มี gene state → หารด้วย 6
cov   = (hs + hr + ha + hst) / denom;
score = round(cov*60 + man*15 + tl*15 + big*10); // เต็ม 100
// A+ ≥85 · A ≥70 · B ≥55 · C ≥40 · D <40

ผลจริง: XMR/GRIN/EPIC/MWC/XTM = 100 · AZTEC/ALEO/OCT = 90 · ZEC = 75 · DASH/TORN = 45 · MYST = 15

หมายเหตุที่ฝังในหน้าเว็บ: คะแนนวัด "ความแข็งของกลไก" ไม่ได้วัดมูลค่า/การลงทุน/ทีม

4.3 ข้อตกลงความซื่อตรงในการ curated (ทำตามสัญญาตลอดมา)

  1. ไม่เดา — ไม่มีหลักฐาน → ทิ้งว่าง — หรือไม่ใส่ (ตัวอย่าง: 3 เหรียญไม่มี GitHub repo ที่มั่นใจ → ไม่มี dev stats)
  2. แสดงที่มาของ repo — ถ้าดึงจากระดับ org การ์ดบอก "repo ดาวมากสุดใน org"
  3. ระบุถึงกรณีพิเศษ — XVG (IP-level), TORN (sanctioned), AZTEC (alpha + vuln) ถูกทำเครื่องหมายชัดเจนในหน้าที่มี
  4. numeric เกี่ยวกับตลาดทุกตัวมี timestamp + แหลมา (CoinGecko snapshot ใน stats bar)

13. Environment gotchas (เจอแล้วแก้ไปแล้ว)

  1. Git Bash /tmp มองไม่เห็นสำหรับ Windows python — เขียนไฟล์ temp ใน workspace เสมอ (ใช้ data/_check.js แทน /tmp/x.js)
  2. WebFetch คืนempty สำหรับ JSON API — ใช้ curl ทาง Bash แทน
  3. heredoc โยงเข้า python.exe ตรงๆ อาจโดนบล็อก — เขียน .py ด้วย Write tool แล้วรัน
  4. CoinGecko 429 — retry + backoff; ปล่อยว่างดีกว่าปลอมตัวเลข
  5. .gitattributes CRLF — git เตือน LF→CRLF บนไฟล์ text ใหม่ (harmless)
  6. git identity ไม่ตั้ง — ส่ง -c user.name/user.email ต่อคอมมิต
  7. ภาษาเกณฑ์/ตัวเลขเพี้ยน — build/verify ผ่าน grep (เช่น CJK scan ก่อน commit)

PRIVACY//TERMINAL

A single-file research terminal for pure-privacy crypto assets.

51 assets where privacy is the protocol's core purpose — no ZK-rollup infrastructure, no general-purpose L1s that merely flirt with privacy. Every row carries a hand-built DNA profile: what the cryptography actually hides, what you have to trust, the shape of the anonymity set, the security history and the regulatory posture.

🔴 Live: akaradje.github.io/privacy-terminal — one self-contained HTML file, no build step, no dependencies, works offline.

What's inside

Hand-classified into four families — the only inclusion rule is that privacy is the protocol, with a publicly verifiable mechanism:

Everything else in CoinGecko's privacy categories — ZK rollups, general L1s, adjacent tooling — is deliberately excluded (200 assets cut) because it is not privacy by design.

2. DNA profiles (52, hand-curated from project documentation)

Click any row to open the dossier:

  • Gene strip — what is hidden (sender / receiver / amount / state), each marked FULL (always) or OPT (opt-in); mandatory? trustless? (no trusted setup / TEE / committee)
  • primitive — the actual cryptography (Halo 2, RingCT+CLSAG, MimbleWimble, TFHE, MPC, TEE, mixnet…)
  • trust assumption · anonymity set · audit · governance · security history · compliance · stage · event timeline
  • Project dossier — description, nine link channels (website / whitepaper / GitHub / X / Telegram / Discord / Reddit / forum / explorer), 7-day price sparkline, and dev activity pulled from the GitHub API (stars, forks, open issues, language, last commit, licence)

3. DNA Matrix

A gene-by-gene comparison table of all 51 assets with a transparent, computed score:

coverage (what is hidden) ÷ applicable max × 60  +  mandatory 15  +  trustless 15  +  network-wide anonymity set 10  =  100

The rubric is printed on the page. Scores measure mechanism strength, not value or investment merit. Notable outcomes: XMR / GRIN / EPIC / MWC / XTM = 100, AZTEC / ALEO / OCT = 90, ZEC = 75 (opt-in, pool-based), DASH / TORN = 45.

4. Terminal UX

Single view, sortable columns, /-to-focus search that reaches into the DNA text (mimblewimble, sgx, ringct, trusted setup, ofac), mcap and DNA-grade filters, j/k + Enter keyboard navigation, 7-day sparklines inline, and a ⟳ LIVE button that re-fetches prices from CoinGecko in the browser.

Rebuild

The repository contains the full pipeline, not just the built page — a clone is enough:

git clone https://github.com/akaradje/privacy-terminal.git && cd privacy-terminal

bash scripts/snapshot.sh        # market snapshot, all 8 privacy categories -> data/cat_*.json
python data/fetch_detail.py     # dossiers + 7d sparklines from CoinGecko -> data/detail/*.json
python data/enrich_gh.py        # GitHub dev stats (stars/forks/issues/last commit)
python validate.py              # data-contract check — must exit 0 before you build
python build.py                 # template.html + app.js + data/* -> privacy-terminal.html

privacy-terminal.html is the deployable artefact; a copy lives at index.html, which GitHub Pages serves.

validate.py enforces the data contract: every asset in data/tiers.json needs a CoinGecko id, a dossier and complete gene flags; gene ranges are checked (hs/hr/ha/hst ternary, man/tl/big/nst binary); nst=1 together with hst>0 is rejected; DNA scores must stay inside 0–100. Current state: 51 assets, 0 errors, 0 warnings.

Data refreshes automatically every day at 01:00 UTC via .github/workflows/refresh.yml (snapshot → dossiers → GitHub → validate → build → commit if changed).

Colour convention

Green = up, red = down (international crypto standard). Non-price semantics (sanction/severity badges) use their own colours and are deliberately decoupled from the price convention.

Limits

  • Prices snapshot to the data timestamp; the LIVE button needs a browser with internet access.
  • CoinGecko's free tier no longer serves community/developer data, so dev activity comes from GitHub directly.
  • DNA profiles are summaries for screening, not security audits — read each project's own documentation before acting.
  • One sparkline (DERO) is missing due to API rate limiting.
Disclaimer — All data is compiled from public sources (CoinGecko, GitHub) for research and screening only. Nothing here is financial advice or a recommendation to buy or sell. Digital-asset markets are highly volatile; do your own research and verify each project's own documentation before acting.
